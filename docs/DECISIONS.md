# Week 13 decisions by topic

These are prototype implementation choices, not instructor-prescribed tools or operational policy. The instructor accepts the assessment; actual stakeholder acceptance and production use are not claimed. Functional fit, security, reliability, performance, effort/skills, ownership and verification tradeoffs are compared in the [main report](WEEK-13-REPORT.md).

## Topic 1 boundary and architecture

Context: four time-based outputs must remain explainable in one individual project. Decision: Flutter client, authorized Laravel domain API, MariaDB durable work/audit and an independent loopback receiver. Alternative: keep the service call inside the domain request transaction. That is feasible but couples request completion and DB lock duration to a failing dependency. Separating discovery/claim/call/result needs more durable state and receipt reconciliation. Evidence: workflow audit rollback tests, scan atomicity, real receiver outage/retry and UI record boundaries. Review when integration partners, workload or organizational approval change. See the boundary diagram and trust/credential labels in DESIGN.md and architecture.png.

## Topic 2 trigger and execution

Context: edits and the passage of time are different triggers. Decision: immediate request-driven domain validation plus minute scans and a bounded DB worker; first-scan daily Manila snapshot. Alternatives: nightly export/import for decisions, event-only deadline discovery and per-change summary recalculation. They are feasible with different latency/reporting contracts; an event-only approach still needs a due-time/catch-up mechanism. Current configuration bounds candidates and batches but depends on an operator actually starting execution. Evidence: first/repeat/scheduled scan, Manila rollover tests and Activity1 comparison. Review if required latency or observed queue age exceeds the measured scope; no continuous-run SLA established.

## Topic 3 retry and recovery

Context: an error response may follow acceptance, and a successful domain commit may precede logging failure. Decision: one bounded call per reserved journal attempt, stable identity/receipt, finite backoff/cycles and coordinator review; a separate log_status reports post-commit telemetry failure. Alternative: retry each failure immediately inside the HTTP client and return generic failure after any post-commit exception. That is straightforward but obscures the true call budget and committed state. The chosen approach requires a retained receiver ledger and an active human review path. Evidence: same-receipt lost-ack/timeout recovery, no fourth exhausted call, expired claim test and the Activity2 before/after logging test. Review after real competing-worker, process-kill and ledger-restore tests. A global circuit breaker and remote compensation are not implemented.

## Topic 4 protected configuration

Context: Flutter is public, while API/worker/receiver need confidential DB/service settings and separate test isolation. Decision: fresh ignored environment files with sanitized examples, lockfiles, scoped app/test accounts and server role/record policies. Alternative: inject the same secrets only as process environment variables. That avoids persistent configuration files but needs reliable coordination across API, CLI, test and receiver processes; it does not remove rotation/ownership duties. Neither method makes local HTTP safe for production. Current file configuration is reproducible for this classroom environment, but OS-user access and runtime DDL privileges remain limits. Evidence: ignore/exact-value checks, no-secret source/screenshots, API permissions and the pre-RefreshDatabase isolation guard. Review before deployment, credential rotation or environment/privilege changes. No vault, automated rotation or independent vulnerability-audit result is claimed.

## Topic 5 observability and maintainability

Context: a maintainer must distinguish pending, accepted, retrying, exhausted and unknown/partial outcomes. Decision: structured safe JSON plus stable work correlation and durable DB attempt/recovery history; derive bounded metrics from retained records. Alternative: plain unstructured CLI/file messages with manual record inspection. Both are feasible at this scale, but plain messages complicate correlation and reproducible counts. Structured fields add schema/retention responsibility and unmeasured storage/processing overhead. The new log_status prevents a durable DB action being confused with a healthy operational log. Evidence: safe logs, derived indicators, current64-test regression and source change-impact record. Review when retention, workload or queue-age requirements are defined. There is no production dashboard, alert delivery, sustained throughput/resource benchmark or formal maintainability score.
